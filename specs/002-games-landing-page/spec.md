# Feature Specification: Games Landing Page and Game-First Room Setup

**Feature Branch**: Not created (no branch hook is configured)

**Created**: 2026-10-30

**Status**: Draft

**Input**: User description: "Adjust my current requirement to incorporate a games landing page as per the attached screenshot. Make it look attractive and yet professional. When the host selects a game tile, only then the host should be presented with options to either play against the AI, or be presented with the controls to create private rooms and send invitation. For creating room host should have an option to select number of players who can join and play the selected game."

**Builds on**: [001-base-platform-experience](../001-base-platform-experience/spec.md). Where this
feature changes a base requirement, the change is listed under "Changes to Existing Requirements".

## Clarifications

### Session 2026-10-30

- Q: How far should the new purple-and-gold look go? → A: The whole app (landing page, lobby,
  dialogs, and recovery screens), in light and dark modes.
- Q: Which product name does the page use? → A: myArena Hub, with the tagline "Your Friends. Your
  Arena." from the reference.
- Q: How do game tiles get their artwork? → A: Illustrations generated by the app from a fixed
  set of icons and colors chosen by each game, with no image files to supply.
- Q: How is a playable game made available for device testing before real games ship? → A: A
  clearly labelled test game may be shown as playable on a preview deployment only, switched on
  by an explicit setting that is off by default. It never appears on the real service.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Browse the games and pick one (Priority: P1)

A visitor opens the site and lands on a polished page that introduces the platform and shows the
available games as tiles. Games that can be played today are grouped under "Playable Games".
Games that are planned but not ready are grouped under a separate "Future Arena Catalog" and are
clearly marked "Coming soon". Each tile shows what the visitor needs to decide: the game's name, a
short description, artwork, how many people can play, roughly how long a game takes, and which
ways it can be played. Selecting a playable tile chooses that game.

**Why this priority**: Everything else in this feature starts from choosing a game. The landing
page is the first impression of the platform, so it also carries the "attractive yet professional"
goal.

**Independent Test**: Open the site with no room. Confirm the tiles are grouped as described, each
shows its details, a playable tile can be selected, and a "Coming soon" tile cannot start anything.

**Acceptance Scenarios**:

1. **Given** a visitor opens the site, **When** the page loads, **Then** they see the product
   name and tagline, a short statement that no account is needed and that rooms work on phones
   and desktops, a way to join with a room code, and the games grouped into "Playable Games" and
   "Future Arena Catalog".
2. **Given** a playable game tile, **When** the visitor reads it, **Then** it shows the game's
   name, description, artwork, player range, typical duration, the ways to play (for example
   "Solo vs AI & Online"), and a "Playable" status.
3. **Given** a "Coming soon" tile, **When** the visitor selects or activates it, **Then** no game
   or room is started and a short message explains the game is not available yet.
4. **Given** no tile has been selected, **When** the visitor looks at the page, **Then** no room
   creation controls, player-count control, or play-against-AI action is shown.

---

### User Story 2 - Choose how to play the selected game (Priority: P1)

After selecting a playable tile, the host is shown the ways to play that game, and only then. They
can choose to play against the AI, or to create a private room and invite others. Choosing a
different tile changes the options to match that game. Only the options the game really supports
are offered.

**Why this priority**: This is the core interaction the product owner asked for: options appear
only after a game is chosen, so the first screen stays simple and every option is about a known
game.

**Independent Test**: Select a game that supports both modes, then one that supports only one.
Confirm the options shown match each game and that nothing is offered before a selection.

**Acceptance Scenarios**:

1. **Given** the visitor selects a playable tile, **When** the selection is made, **Then** the tile
   is clearly shown as selected and the play options for that game appear next to or below the
   tiles without hiding them.
2. **Given** a game that supports both solo play against the AI and online rooms, **When** it is
   selected, **Then** the visitor sees both "Play against AI" and "Create private room".
3. **Given** a game that supports only one mode, **When** it is selected, **Then** only that mode
   is offered, with a short note saying the other is not available for this game.
4. **Given** the visitor has selected a game, **When** they select a different playable tile,
   **Then** the options update to the new game and anything entered for the previous game is
   cleared.
5. **Given** the visitor has selected a game, **When** they dismiss the selection, **Then** the
   page returns to the state where no options are shown.
6. **Given** the visitor chooses "Play against AI", **When** the game starts, **Then** they play
   that game's solo mode against the AI without creating a shared room or an invitation.

---

### User Story 3 - Create a private room with a chosen number of players (Priority: P1)

Having chosen "Create private room", the host sets how many players can join and play, enters
their display name, and creates the room. The room is created for the selected game and holds
exactly the number of players the host chose. The host receives the room code and invite link to
share, as in the base platform, and arrives in the lobby with the game already selected.

**Why this priority**: Choosing the player count up front is the second explicit requirement, and
it turns the landing page into a working path to a playable room.

**Independent Test**: Select a game, choose "Create private room", pick a player count, create the
room, have people join until it is full, and confirm one more person is turned away with a clear
message.

**Acceptance Scenarios**:

1. **Given** the visitor chose "Create private room" for a game, **When** the controls appear,
   **Then** they include a display name, a number-of-players choice, and a create action, and show
   the allowed range for that game.
2. **Given** a game that allows 2 to 4 players, **When** the host views the number-of-players
   choice, **Then** only values from 2 to 4 can be chosen, and a sensible default is preselected.
3. **Given** a game whose range is wider than the platform's room limit, **When** the host views
   the choice, **Then** the choices stop at the platform's room limit and the page says so.
4. **Given** the host chose a player count and created the room, **When** the lobby opens,
   **Then** the game is already selected, the player limit equals the chosen number, and the
   invitation code and link are available to share.
5. **Given** a room created for a certain number of players, **When** that many people have
   joined, **Then** the next person who tries to join receives the clear full-room message.
6. **Given** the host enters an invalid display name or an out-of-range player count, **When**
   they try to create the room, **Then** the problem is explained in plain language with a safe
   next step and no room is created.

---

### User Story 4 - Join with a room code from the landing page (Priority: P2)

A visitor who was given a room code can enter it from the landing page without choosing a game.
The game comes from the room they join. A visitor who opens an invite link goes straight to
joining and does not have to use the landing page.

**Why this priority**: Joining is half of the platform's purpose and must remain one step away,
but it already works and only needs a home on the new page.

**Independent Test**: From the landing page, use "Join with Room Code" with a valid code and with
an invalid one, and open an invite link directly.

**Acceptance Scenarios**:

1. **Given** the landing page with no game selected, **When** the visitor chooses "Join with Room
   Code", **Then** they can enter a code and a display name without selecting a game.
2. **Given** an invalid, revoked, or closed code, **When** they try to join, **Then** the same
   clear, non-revealing explanation as in the base platform is shown with a safe retry.
3. **Given** a visitor opens an invite link, **When** the link loads, **Then** they go directly to
   joining that room.

---

### User Story 5 - An attractive, professional, accessible page on every device (Priority: P2)

The landing page looks polished and trustworthy: a consistent visual identity, clear hierarchy,
considered spacing, and artwork that makes each game inviting without crowding the text. It works
on laptops, Android phones, and iPhones in portrait and landscape, in light and dark modes, with
mouse, trackpad, keyboard, and touch, and for people who use assistive technology or prefer
reduced motion.

**Why this priority**: The owner asked for a page that is attractive yet professional, and the
platform's principles require accessibility and mixed-device support. It refines the first three
stories rather than adding a new capability.

**Independent Test**: Review the page on real laptop, Android, and iPhone devices in both
orientations and both color modes, operate it by keyboard alone and with a screen reader, and
turn on reduced motion.

**Acceptance Scenarios**:

1. **Given** a narrow phone screen, **When** the page is shown, **Then** tiles stack in a single
   column, nothing requires horizontal scrolling, and the selected game's options are reachable
   without losing sight of which game is selected.
2. **Given** a wide screen, **When** the page is shown, **Then** tiles use the space in several
   columns and the page still reads clearly.
3. **Given** keyboard-only use, **When** the visitor tabs through the page, **Then** every tile
   and control can be reached and activated, with a visible focus indicator.
4. **Given** a screen reader, **When** the visitor reaches a tile, **Then** its name, status
   ("Playable" or "Coming soon"), and whether it is selected are announced, and the appearance of
   the play options is announced.
5. **Given** the visitor prefers reduced motion or has turned decorative effects off, **When** the
   page is used, **Then** no non-essential motion is shown and nothing depends on it.

---

### User Story 6 - Remembered name and preferences (Priority: P3)

The page header shows the visitor's display name and lets them switch decorative visual effects
and sound preference on or off. A name entered once is remembered on that device and prefilled
the next time. None of this is an account and none of it is shared with other people.

**Why this priority**: It smooths repeat visits but is not needed to play.

**Independent Test**: Enter a name, create a room, return to the landing page, and confirm the
name is prefilled; toggle effects and sound and confirm they persist after a refresh.

**Acceptance Scenarios**:

1. **Given** a visitor has used a display name on this device, **When** they return to the page,
   **Then** the name is shown in the header and prefilled in create and join forms, and they can
   change it.
2. **Given** the visitor turns decorative effects off, **When** they refresh or return later,
   **Then** effects stay off on that device.
3. **Given** the visitor changes the sound preference, **When** they start a game, **Then** the
   game can read the preference (this feature adds no sound of its own).
4. **Given** the visitor clears the site's stored data, **When** they return, **Then** the page
   behaves as for a first visit.

### Edge Cases

- No game is playable yet: the page still loads, shows every game as "Coming soon", explains that
  games are on the way, and keeps "Join with Room Code" available.
- The list of games cannot be loaded: the page explains the problem, offers a retry, and keeps
  joining by code available.
- A game becomes unavailable between being selected and a room being created: creation is
  refused with a clear explanation and the visitor returns to the games with no half-created
  room.
- A game's minimum is 1 player (for example a game that can also be played alone): a private
  room still needs at least 2 seats, so the choice starts at 2.
- The visitor selects a tile, enters a name and player count, then selects another tile: the new
  game's options and defaults replace the old ones; the display name is kept.
- The visitor activates a "Coming soon" tile with a keyboard or by touch: nothing starts and the
  explanation is announced to assistive technology.
- The service is at capacity, a room cannot be created, or the network drops during creation: the
  base platform's clear errors and safe-retry behavior apply, with no duplicate rooms.
- The device still holds a seat in an active room: the page offers a clear way back to that room
  instead of leaving the visitor to find it.
- A visitor arrives from an invite link while a game tile was previously selected: the invite
  takes priority and the earlier selection is ignored.
- Very long game names or descriptions, very small screens, increased text size, or both
  orientations: text wraps, controls stay usable, and nothing overflows horizontally.

## Requirements *(mandatory)*

### Functional Requirements

**Landing page and catalog**

- **FR-001**: The site's front page for a visitor who is not currently in a room MUST be the games
  landing page.
- **FR-002**: The landing page MUST show the product name and tagline, a short statement that no
  account is needed and that rooms work on phones and desktops, and an always-available "Join
  with Room Code" action.
- **FR-003**: The landing page MUST show the games in two groups: games that can be played now
  ("Playable Games", marked ready to play) and games that are planned ("Future Arena Catalog",
  marked "Coming soon").
- **FR-004**: Each game tile MUST show the game's name, a short description, artwork, the range of
  players, a typical duration, the ways the game can be played, and a status of "Playable" or
  "Coming soon".
- **FR-005**: A game MUST be shown as "Playable" only if a room or solo game can really be started
  for it today; every other game MUST be shown as "Coming soon". The page MUST NOT offer play
  options for a "Coming soon" game. The one exception is a test game on a preview deployment,
  which MUST be labelled as a test game.
- **FR-006**: Activating a "Coming soon" tile MUST start nothing and MUST explain that the game is
  not available yet.
- **FR-007**: The tiles MUST come from the games the platform knows about, with each game
  supplying its own name, description, artwork, player range, duration, supported ways to play,
  and status. Adding or retiring a game MUST change the page without redesigning it.

**Game-first options**

- **FR-008**: Until a playable tile is selected, the page MUST NOT show room creation controls, a
  player-count control, or a play-against-AI action. Any shortcut near the top of the page for
  creating a room or playing alone MUST direct the visitor to choose a game first rather than
  present those controls.
- **FR-009**: Selecting a playable tile MUST mark it as selected and MUST then present only the
  ways to play that game supports: "Play against AI" where the game offers solo play, and "Create
  private room" where the game offers online rooms.
- **FR-010**: If a game supports only one way to play, the page MUST offer only that way and MUST
  say briefly that the other is not available for this game.
- **FR-011**: Selecting a different tile MUST replace the options with the new game's, clear any
  choices entered for the previous game, and keep the display name. The visitor MUST be able to
  dismiss the selection and return to the state with no options shown.
- **FR-012**: "Play against AI" MUST start that game's solo mode against the AI without creating a
  shared room or invitation and without an account. The AI opponent and its rules belong to the
  game, not to this feature.

**Creating a private room**

- **FR-013**: "Create private room" MUST present a display name, a number-of-players choice, and a
  create action for the selected game.
- **FR-014**: The number-of-players choice MUST allow only values the selected game supports: from
  its minimum (but not fewer than 2) up to its maximum (but not more than the platform's
  100-player room limit). It MUST show the allowed range, offer a default, and explain a capped
  range when the platform limit applies.
- **FR-015**: Creating the room MUST create it for the selected game with the chosen number as its
  player limit. The host MUST receive the room code and invite link as in the base platform and
  MUST arrive in the lobby with the game already selected and the limit applied.
- **FR-016**: A room MUST hold no more players than the chosen limit, and a person who tries to
  join a full room MUST receive the clear full-room message from the base platform.
- **FR-017**: Invalid input, an unavailable game, a full service, or a network failure during
  creation MUST be explained in plain language with a safe next step, MUST NOT leave a
  half-created or duplicate room, and MUST keep what the visitor entered.

**Joining**

- **FR-018**: A visitor MUST be able to join with a room code from the landing page without
  selecting a game, and MUST receive the base platform's non-revealing errors for unusable codes.
  Invite links MUST continue to go directly to joining.
- **FR-019**: If this device still holds a seat in an active room, the landing page SHOULD offer a
  clear way back to it.

**Name and preferences**

- **FR-020**: The page MUST show the visitor's display name in the header once one is known, MUST
  prefill it in create and join forms, and MUST let the visitor change it, applying the base
  platform's name rules. The name MUST be remembered only on the visitor's own device and MUST NOT
  be treated as an account or identity.
- **FR-021**: The page MUST let the visitor turn decorative visual effects on or off and set a
  sound preference, MUST remember both on the device, and MUST make the sound preference
  available to games. This feature adds no audio of its own.

**Look, devices, and accessibility**

- **FR-022**: The landing page MUST have a consistent, professional visual identity: a clear
  hierarchy, even spacing, readable type, and artwork that supports the text without replacing
  it. It MUST work in both light and dark modes with legible text and controls. The same visual
  identity MUST be applied across the rest of the app (lobby, dialogs, and recovery screens) so
  the product feels like one.
- **FR-023**: The layout MUST adapt from a single column on narrow phones to multiple columns on
  wide screens, in portrait and landscape, without horizontal scrolling, and MUST keep the
  selected game and its options in view together.
- **FR-024**: Every tile and control MUST work with mouse, trackpad, keyboard, and touch, MUST show
  a visible focus indicator, and MUST be large enough to touch reliably.
- **FR-025**: Tile names, statuses, and selected state, the appearance of play options, and every
  error MUST be available to assistive technology. Status MUST NOT be conveyed by color alone.
  Core flows MUST meet WCAG 2.2 AA contrast and focus requirements.
- **FR-026**: The page MUST honor reduced-motion preferences and MUST NOT depend on motion or
  decorative effects to be understood. When reduced motion is requested, decorative effects MUST
  default to off.
- **FR-027**: The page MUST become usable quickly, MUST show readable content and tiles before
  artwork finishes loading, and MUST NOT load any game's own content until that game is chosen to
  be played.

**Separation, privacy, and evidence**

- **FR-028**: The landing page MUST contain no game rules. Everything game-specific it shows MUST
  come from what each game supplies about itself.
- **FR-029**: Nothing about the visitor beyond the display name and preferences described here
  MUST be stored, and none of it MUST be shown to other people.
- **FR-030**: Acceptance evidence for this feature MUST cover the landing page, selecting a game,
  both play options, room creation with a chosen player count, and joining by code, on a real
  laptop, a real Android phone, and a real iPhone, in portrait and landscape, with keyboard-only,
  screen-reader, and reduced-motion checks, recorded with device, operating system, browser and
  version, tester, date, and result. Viewport emulation MUST NOT substitute for the phones.

### Key Entities *(include if feature involves data)*

- **Game Catalog Entry**: What the landing page knows about one game: name, short description,
  artwork, player range, default player count, typical duration, the ways it can be played (solo
  against the AI, online private room), a category label, and a status of Playable or Coming
  soon. Each game supplies its own entry.
- **Play Option**: One way to play a selected game, either "Play against AI" or "Create private
  room". Offered only when the game supports it.
- **Room Setup Choices**: What the host provides to create a room: the selected game, a display
  name, and the number of players. Used once to create the room.
- **Visitor Preferences**: A display name, a decorative-effects setting, and a sound setting kept
  on the visitor's device only.

## Changes to Existing Requirements

This feature amends the base platform ([spec](../001-base-platform-experience/spec.md)) as
follows. Everything not listed there is unchanged.

| Base requirement | Change |
|------------------|--------|
| Base User Story 1, scenario 1 and FR-001 (create a room with a display name) | Creating a room now starts from a selected game tile and a chosen number of players, then asks for the display name. Joining with a code or link is unchanged. |
| Base FR-005 (host selects an available game, manages settings) | The game is now chosen before the room exists and arrives pre-selected in the lobby. The host can still change the game and the player limit in the lobby under the base rules, and the limit still cannot drop below the number of people already seated. |
| Base FR-019 and room settings (limit of 1 to 100, default 100) | The player limit is now chosen when the room is created, within the selected game's range and never above 100. Its default comes from the selected game instead of always being 100. |
| Base entry screen (side-by-side create and join forms) | Replaced by the landing page. The fields, validation, and error messages of the forms carry over. |
| Base FR-020 (platform separate from game rules) | Games now also supply presentation details (name, description, artwork, duration, supported ways to play, status) so the landing page can show them. Rules stay with the games. |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In moderated sessions, at least 90% of first-time visitors choose a game and create a
  private room for it, without help, within 60 seconds of the page loading.
- **SC-002**: Before a tile is selected, 0 room creation controls, player-count controls, or
  play-against-AI actions are visible; after selecting a playable tile, 100% of the options shown
  match what that game supports, checked for every playable game.
- **SC-003**: In 100% of rooms created with a chosen player count, the room accepts exactly that
  many players and gives the next person to join the clear full-room message.
- **SC-004**: 100% of attempts to activate a "Coming soon" tile start nothing and show an
  explanation.
- **SC-005**: In a review by at least 5 people outside the project team, the page's average rating
  for "looks attractive" and for "looks professional" is at least 4 out of 5 on each.
- **SC-006**: On the acceptance phones over a typical mobile connection, the games and their
  details are visible and selectable within 3 seconds for at least 95% of page loads.
- **SC-007**: In 100% of portrait and landscape checks on Android and iPhone, the page has no
  horizontal scrolling and the selected game and its options are reachable.
- **SC-008**: Keyboard-only and screen-reader acceptance completes the journey from the landing
  page to a created room, and in 100% of checks each tile's name, status, and selected state is
  announced and every error is announced with a next step.
- **SC-009**: With reduced motion requested, no non-essential motion appears and decorative
  effects are off by default in 100% of checks.
- **SC-010**: 100% of the real-device acceptance matrix in FR-030 is recorded for laptop, Android,
  and iPhone; emulation does not count toward this result.

## Assumptions

- The attached screenshot sets the content and hierarchy: a header with the name, sound and
  effects controls, and the visitor's name; a hero with the tagline, a short value statement, and
  the actions "Create Private Room", "Join with Room Code", and "Play Solo vs AI"; a "Playable
  Games" group; and a "Future Arena Catalog" group. It is design direction, not a pixel-exact
  layout.
- Because options must appear only after a game is chosen, the hero's "Create Private Room" and
  "Play Solo vs AI" shortcuts guide the visitor to choose a game first; they do not open the
  creation controls themselves. "Join with Room Code" needs no game and opens directly.
- The product name is myArena Hub with the tagline "Your Friends. Your Arena." (the reference's
  "myArena Royalty" is not used). The name and tagline are content that can change without
  redesign.
- Ludo, Snakes & Ladders, and Tambola are delivered by their own game features. A tile shows
  "Playable" only once its game can really be started; until then it shows "Coming soon". This
  feature is not blocked on those games and is accepted with whichever games are available, plus
  a labelled test game that exists only on preview deployments.
- The four roadmap tiles in the reference (a drawing-and-guessing game, a chess game, a dice game,
  and a four-in-a-row game) are placeholders. They carry no commitment or dates and appear only
  as "Coming soon".
- The player ranges, durations, and modes in the reference are examples. The real values come from
  each game.
- The AI opponent, its difficulty, and its rules are owned by each game. This feature only
  provides the way in.
- A private room needs at least 2 seats, and the platform keeps its limit of 100 players per room.
- A game's default player count is supplied by the game; if it supplies none, its maximum
  (capped at 100) is used.
- The display name and preferences are stored only on the visitor's device. Clearing site data
  resets them, and they are not an account.
- The landing page follows the platform's rules for light and dark modes, device support, and
  accessibility, and needs real-device acceptance like every feature.
